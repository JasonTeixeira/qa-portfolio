# 构建产品界面与系统地图

当你不再把产品视为一堆屏幕的堆砌时，构建它会变得更容易。

从两张地图开始：

1. 界面地图
2. 系统地图

界面地图展示用户接触的内容。

系统地图展示支撑产品运行的内容。

:::system-diagram title="产品构建地图" label="界面 <-> 系统" nodes="界面,状态,规则,验证"
界面是用户所见的内容。状态、规则、集成和验证则让界面变得可信且可维护。
:::

## 界面地图

界面地图列出了面向用户的流程。

对于 SaaS 产品，可能包括：

- 首页
- 注册
- 新手引导
- 仪表盘
- 计费
- 设置
- 报告
- 支持

对于内部工具，可能包括：

- 录入表单
- 工作队列
- 详情页面
- 审批面板
- 管理后台
- 导出

界面地图帮助你了解产品要求用户做什么。

## 系统地图

系统地图列出了运行层：

- 认证
- 角色
- 数据模型
- 后台任务
- 集成
- 事件
- 分析
- 计费
- 权限
- 错误处理
- 审计日志

这是构建者经常低估范围的地方。

他们设计了仪表盘却忘了队列。

他们编写了 AI 提示词却忘了评估。

他们构建了结账流程却忘了 webhook 重试。

:::proof-note title="Nexural 示例" label="凭证"
Nexural 是一个很好的参考，因为界面可见，但重要的工作都在底层：185 个数据库表、69 个 API 端点、Stripe 计费、实时工作流、Discord AI 以及 61 个测试套件。
:::

## 绘制失败路径

一份好的系统地图包含出问题时的应对方案。

示例：

- 支付失败
- webhook 重试
- 模型拒绝响应
- 用户缺少权限
- 源数据过期
- 集成超时
- 管理员需要覆盖操作
- 邮件退回

如果一个产品没有失败路径，它仍然只是一个演示品。

:::checklist title="系统地图检查清单" label="构建准备"
- 主要的用户流程有哪些？
- 每个流程读取或写入什么数据？
- 哪些权限控制着该操作？
- 点击后运行什么后台任务或集成？
- 失败时会发生什么？
- 有什么凭证能证明系统正在运行？
:::

## 将地图转化为构建顺序

系统地图应决定构建顺序。

通常是：

1. 数据模型
2. 认证和角色
3. 核心工作流
4. 界面
5. 集成
6. 分析
7. 凭证和文档

这个顺序不如从炫酷的屏幕开始那么令人兴奋，但它更持久。

:::scorecard title="纯界面 vs 系统主导的构建" label="学院"
| 层面 | 纯界面方式 | 系统主导方式 |
| --- | --- | --- |
| UI | 漂亮的屏幕 | 可用的工作流 |
| 数据 | 临时字段 | 命名模型 |
| AI | 提示框 | 评估驱动的助手 |
| 计费 | 结账按钮 | 生命周期处理 |
| 发布 | 凭感觉 | 凭证面板 |
:::

## 这对学院为何重要

学院路径应直接教授这种模型。

DIY 构建者不仅需要技巧。

他们需要学习如何将一个想法转化为产品界面、系统地图、凭证面板和增长循环。

这就是"我做了一个东西"和"我构建了一个系统"之间的区别。
