SAGE IDEAS DISCORD RAG, ML, AND AI OPERATING SYSTEM MASTER PLAN
Version: 2026-06-24
Scope: Sage Ideas Discord, SageBot, RAG, ML scoring, content engine, engagement engine, admin operations, observability, evaluation, and high-end community management.

PURPOSE
Build Sage Ideas Discord into a world-class education community operating system.

The system should not feel like a Discord with a bot attached. It should feel like a live academy, build lab, coaching layer, content studio, and intelligence dashboard running together.

The final system must:
1. Keep the server lean and easy to understand.
2. Approve and route members cleanly.
3. Know what each member is trying to build.
4. Answer questions from verified knowledge.
5. Capture useful questions, answers, builds, reviews, wins, and resources.
6. Turn community activity into daily posts, quizzes, challenges, recaps, articles, and lessons.
7. Reward genuinely useful participation.
8. Detect weak, generic, unsafe, or unsupported AI output before it reaches members.
9. Give admins one operating dashboard for members, content, approvals, RAG health, jobs, points, challenges, and premium workflows.
10. Prove quality with tests, evals, traces, evidence files, and live verification.

NORTH STAR
SageBot should become the operating system for the server:

member joins -> application -> approval -> onboarding -> path/level routing -> first-week checklist -> daily prompt -> quiz/challenge -> project submission -> feedback -> points -> leaderboard -> content queue -> RAG sync -> daily/weekly content -> public growth loop -> improved curriculum

NON-NEGOTIABLE QUALITY BAR
1. No generic AI content reaches public channels.
2. Every AI answer cites retrieved source chunks when it claims facts.
3. Every generated draft passes a quality/eval gate before posting.
4. Every admin action logs actor, target, timestamp, result, and failure reason.
5. Every role action is backed by database state or Discord-native approval state.
6. Every point action has an idempotency key and anti-farming guard.
7. Every scheduled job is idempotent and visible in admin.
8. Every failure path writes evidence: log, event row, dead letter, or dashboard warning.
9. No unapproved member should see free-member channels.
10. RAG must prefer approved docs/resources/content queue items over random unreviewed chatter.
11. Community content should come from real member activity, not empty calendar filler.
12. "Done" means tested, verified, and evidence captured.

KEY SDKS, REPOS, AND TOOLS TO USE

Primary stack to keep:
1. Next.js / TypeScript
2. Supabase Postgres + pgvector
3. DeepSeek for generation
4. Discord API/Gateway
5. Current SageBot command and admin dashboard architecture

Add in phases:
1. Langfuse
   - Purpose: LLM observability, traces, prompt versions, eval scores, cost/latency tracking.
   - Docs: https://langfuse.com/docs
   - Use for: every `/ask-sage`, draft generation, retrieval, eval, content approval, and admin action trace.

2. DeepEval
   - Purpose: CI-style LLM/RAG tests.
   - Docs: https://deepeval.com/
   - Use for: answer correctness, hallucination, contextual relevance, tone/personality, content quality regression tests.

3. Ragas
   - Purpose: RAG retrieval/answer metrics.
   - Docs: https://docs.ragas.io/
   - Use for: context precision, context recall, faithfulness, response relevance, noise sensitivity.

4. Vercel AI SDK
   - Purpose: TypeScript model abstraction, tools, telemetry, streaming, provider switching.
   - Docs: https://ai-sdk.dev/docs/introduction
   - Use for: unifying DeepSeek calls, future model fallback, structured generation, and trace metadata.

5. Zod structured outputs
   - Purpose: strict schemas for AI-generated quizzes, challenges, drafts, profile updates, classifications, and content queue items.
   - Already installed.
   - Use for: every AI output that becomes database state.

6. Instructor.js or equivalent structured-output helper
   - Purpose: typed LLM JSON extraction with validation/retry ergonomics.
   - Repo: https://github.com/567-labs/instructor-js
   - Use only if Zod + direct DeepSeek JSON handling becomes too repetitive.

7. LlamaIndex.TS
   - Purpose: advanced TypeScript RAG ingestion/query abstractions.
   - Docs: https://developers.llamaindex.ai/typescript/framework/
   - Use selectively for document ingestion, metadata extraction, and query workflows if the corpus grows beyond current scripts.

8. LangGraph
   - Purpose: durable stateful agent workflows and human-in-the-loop orchestration.
   - Docs: https://docs.langchain.com/oss/python/langgraph/overview
   - Use later, only if multi-step agent workflows become complex enough to justify it.

9. Trigger.dev
   - Purpose: TypeScript-native background jobs, retries, scheduled tasks, long-running AI workflows.
   - Docs: https://trigger.dev/
   - Recommended first durable job runner for this repo.

10. Temporal TypeScript SDK
   - Purpose: strongest durable execution model.
   - Docs: https://docs.temporal.io/develop/typescript
   - Use later if Trigger.dev is not enough for resume/retry/human approval workflows.

11. BullMQ
   - Purpose: Redis queue, rate limits, repeatable jobs.
   - Docs: https://docs.bullmq.io/
   - Use only if self-managed queue control is preferred over Trigger.dev.

12. Sentry and OpenTelemetry
   - Purpose: app errors, traces, metrics.
   - Sentry is already installed.
   - Use alongside Langfuse: Sentry for app failures, Langfuse for LLM behavior.

ARCHITECTURE DECISION
Do not rewrite the system into Haystack, RAGFlow, or a Python-first stack right now.

Decision:
Keep the current TypeScript/Supabase/Discord architecture and add the missing quality, eval, observability, and workflow layers.

Reason:
1. The current repo already has working Discord, Supabase, RAG, DeepSeek, commands, admin dashboard, and smoke tests.
2. A rewrite would delay the actual operating system.
3. The biggest gap is not framework choice. The gap is proof, observability, evals, reranking, personality, and workflow hardening.

Allowed exceptions:
1. Use Python-only tooling only if it produces clear eval artifacts and does not become the main runtime.
2. Use LangGraph/Temporal only when the simpler TypeScript job runner becomes insufficient.
