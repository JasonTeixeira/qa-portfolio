Build the Sage Ideas Discord into a high-quality education operating system that is measurable, controllable, and useful every day.

This plan exists so we do not drift into ghost code, half-built dashboards, fake jobs, or unverified "done" claims.

The target system is not just:

NON-NEGOTIABLE ENGINEERING RULES
1. No phase is complete without command evidence.
2. No generated code is accepted if no route, job, command, or UI path uses it.
3. No dashboard metric may be invented; it must read live data or clearly say unavailable.
4. No AI output may become public content without a quality gate and approval state.
5. No raw Discord chatter may become authoritative RAG without approval.
6. No point award may exist without an idempotency key.
7. No scheduled job may be non-idempotent.
8. No admin mutation may lack auth, event logging, and a failure path.
9. No member-access workflow may rely on wishful Discord permissions; it must be proven with role state.
10. No "world-class" score may be claimed without the score rubric and evidence artifact.
11. Every phase must leave a "what remains" section, even when it passes.
12. Every external/manual blocker must be named directly.

SCORECARD MODEL

Scoring bands:
- 0-49: not production-worthy
- 50-69: scaffold or partial utility
- 70-84: functional but not high-grade
- 85-91: production useful
- 92-94: high quality
- 95-99: high-end, verified, operationally useful
- 100: reserved for sustained production proof at real scale; do not claim casually

2. Role routing and member state
3. Gateway capture and classification
4. RAG corpus quality
5. Retrieval and answer faithfulness

12. Admin operating dashboard
13. Job reliability and recovery
14. Observability and tracing
15. Premium workflows
16. Growth loop and public proof
17. Security, privacy, and abuse controls
18. Scale readiness

Required evidence for 95+ in any category:
1. Unit tests for core logic.
2. Integration or smoke test for database/Discord/API behavior.
3. E2E test where the user/admin path matters.
4. Production build passes.
5. Evidence JSON written under docs/evidence/discord-ai-os/.
6. Failure cases tested or manually documented.
7. Remaining gaps explicitly listed.

PHASE EXECUTION LOOP
Every phase follows the same loop:

1. Baseline
   - Check current git status.
   - Identify unrelated dirty files.
   - Read relevant modules and evidence.
   - Define exact success criteria.

2. Build
   - Add/modify the smallest complete slice.
   - Prefer existing repo patterns.
   - Avoid unused abstractions.
   - Keep admin actions authenticated.
   - Add idempotency for jobs and points.

3. Verify
   - Run focused tests first.
   - Run broader gates when risk warrants it.
   - Run E2E for UI/admin flows.
   - Run smoke commands for Discord/RAG.

4. Evidence
   - Write phase evidence JSON.
   - Include command outputs, counts, run keys, and honest blockers.
   - Link generated artifacts or screenshots if used.

5. Review
   - Inspect git diff.
   - Ensure no unrelated files are staged.
   - Ensure no secrets are written.
   - Ensure no ghost code exists.

6. Commit
   - Commit only the phase if user wants clean progress.
   - Leave unrelated dirty files untouched.

7. Report
   - What changed.
   - What passed.
   - What failed or remains.
   - Current score changes.
   - Next phase.
