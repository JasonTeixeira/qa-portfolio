SAGE IDEAS RAG + CONTENT INTELLIGENCE SYSTEM BUILD PLAN
Status: Proposed
Date: 2026-06-20
Owner: Sage Ideas
Primary product surfaces: Discord, admin dashboard, content engine, resources, future academy lessons

OBJECTIVE
Build a production-grade RAG system that turns Discord questions, answers, resources, articles, lessons, and admin notes into searchable, cited, reusable knowledge. The system must support high-quality answers, content generation, quizzes, weekly recaps, curriculum/resource creation, and admin review workflows.

CORE DECISION
Use the existing TypeScript/Next/Supabase stack as the primary system.

Recommended stack:
- Supabase Postgres + pgvector for durable storage, source records, chunks, embeddings, logs, and feedback.
- LlamaIndex TS patterns for ingestion, chunking, indexing, retrieval/query engine patterns. Keep implementation local where that is simpler and more testable.
- DeepSeek for generation/content workflows because it is much cheaper for the community/content engine.
- Embeddings are separate from generation. DeepSeek `/embeddings` was probed and returned 404, so the proven local embedding lane uses Transformers.js with `Supabase/gte-small` at 384 dimensions.
- LangGraph later, only after retrieval is reliable, for multi-step agent workflows and human approval loops.
- LangChain only where it provides useful tools/integrations.
- Do not start with Haystack or RAGFlow unless a separate Python/document-processing service becomes necessary for heavy PDF parsing.

CURRENT FOUNDATION ALREADY IN PLACE
- Discord slash commands are registered.
- Discord Gateway worker is deployed on Railway.
- Gateway worker captures Discord Gateway events.
- Reliability tables exist: discord_gateway_heartbeats, discord_gateway_sessions, discord_gateway_dead_letters.
- Content/community tables exist: discord_messages, discord_questions, discord_answers, discord_content_queue, discord_quizzes, discord_challenges, discord_points_ledger.
- Admin Discord dashboard exists.

KNOWN REMAINING PREREQUISITE
- Discord Message Content Intent must be enabled in the Discord Developer Portal before actual message bodies can be captured from normal Discord messages.

PHASE COUNT
Build this in 10 phases.

Each phase must pass its verification gate before the next phase starts.

PHASE 2 - SOURCE REGISTRY AND NORMALIZATION

Objective:
Create a clean source registry that converts Discord/community/content records into consistent RAG source records.

Specs:
- Each source gets stable source_key.
- Each source gets content_hash for dedupe.
- Source text must be normalized but not over-cleaned.
- Preserve original raw IDs and links.
- Preserve channel, author, path, level, category, and quality signals where available.
- Bot messages should be excluded unless explicitly marked as reusable.
- Low-quality messages should be ignored or marked low priority.

Source mapping:
- discord_messages -> source text from message content.
- discord_questions -> source text from structured question.
- discord_answers -> source text from accepted/helpful answers.
- discord_content_queue -> source text from captured ideas and lessons.
- content/blog/*.mdx -> source text from article body and metadata.
- docs/resources later -> source text from resource markdown.

Deliverables:
- lib/rag/source-normalizer.ts
- scripts/rag/sync-sources.ts
- npm script: rag:sync-sources
- docs/evidence/rag/source-sync-sample.json

Tests:
- Unit tests for source_key stability.
- Unit tests for content_hash stability.
- Unit tests for bot-message exclusion.
- Unit tests for Discord source metadata mapping.
- Smoke script inserts or updates sources idempotently.

Exit Gate:
- Running rag:sync-sources twice creates no duplicates.
- Source registry has records from at least Discord and blog/content sources.
- Evidence file shows sample source records with traceable metadata.


PHASE 3 - INGESTION, CHUNKING, AND EMBEDDINGS

Objective:
Turn normalized sources into high-quality chunks and embeddings.

Specs:
- Use local chunking logic wrapped behind lib/rag/chunking.ts first.
- Start with sentence/paragraph-aware chunking.
- Target chunk size: 500-900 tokens equivalent.
- Chunk overlap: 80-150 tokens equivalent.
- Never split code blocks badly if possible.
- Preserve heading/context metadata.
- Store embedding model name and dimension when a real embedding provider is configured.
- Store content_hash per chunk.
- Re-embed only changed chunks.
- Failed embeddings go into ingestion run errors, not silent failure.
- Generation provider is DeepSeek. Embedding provider is not allowed to be faked.
- Proven embedding provider: local Transformers.js `Supabase/gte-small`.

PHASE 4 - HYBRID RETRIEVAL API

Objective:
Build retrieval that combines vector similarity, keyword/full-text search, metadata filters, and ranking.

Specs:
- Do not use vector-only retrieval.
- Query should support:
  - text query
  - source type filters
  - channel filters
  - date range filters
  - minimum quality threshold
  - max results
- Return cited chunks with source IDs and source URLs.
- Log every retrieval request.
- Include ranking features in logs.
- Add confidence estimate based on score spread and source quality.

Deliverables:
- lib/rag/retrieval.ts
- app/api/admin/rag/search/route.ts
- app/api/discord/rag/search/route.ts or internal handler if not public.
- scripts/rag/smoke-retrieval.ts
- npm script: rag:smoke-retrieval

Tests:
- Unit tests for query parsing.
- Unit tests for filter behavior.
- Integration test using seeded chunks.
- Smoke query returns relevant cited chunks.
- Retrieval log row is created.

Exit Gate:
- A real query against live Supabase returns cited chunks.
- Retrieval logs show query, filters, selected chunks, and score metadata.
- No uncited answer path exists yet.


PHASE 5 - ANSWER ENGINE WITH CITATIONS

Objective:
Generate useful answers grounded in retrieved chunks and refuse weakly supported answers.

Specs:
- Every answer must include citations.
- The answer engine must separate:
  - retrieved context
  - answer draft
  - citations
  - confidence
  - recommended follow-up
- If retrieval confidence is low, answer should ask a clarifying question or say the knowledge base does not have enough context.
- No financial/legal/medical advice generation from Discord knowledge.
- Admin and Discord surfaces can share the same core answer engine.

Deliverables:
- lib/rag/answer-engine.ts
- lib/rag/prompts.ts
- app/api/admin/rag/answer/route.ts
- scripts/rag/smoke-answer.ts
- npm script: rag:smoke-answer

Tests:
- Unit tests for citation requirement.
- Unit tests for low-confidence refusal.
- Unit tests for source formatting.
- Smoke answer against known source.
- Retrieval and answer logs are created.

Exit Gate:
- Answer returns citations every time.
- Low-confidence answer refuses or asks clarification.
- Answer log contains prompt version, model, retrieval IDs, and output.

- Answer faithfulness.
- Low-confidence refusal correctness.

PHASE 10 - LANGGRAPH AGENT WORKFLOWS

Objective:
Add multi-step RAG agents only after retrieval, citations, feedback, and evals are stable.

Specs:
- Use LangGraph for stateful workflows that need multiple steps and admin approval.
- Workflows must be deterministic where possible.
- Every tool call must be logged.
- Mutating actions require admin approval.
- Failed runs must be resumable or dead-lettered.

Initial workflows:
- Answer Draft Workflow:
  retrieve -> draft -> cite -> confidence check -> admin approve -> post
- Content Brief Workflow:
  cluster questions -> retrieve sources -> draft brief -> admin approve -> queue
- Resource Builder Workflow:
  find gap -> retrieve examples -> draft resource -> admin approve -> publish to resources
- Weekly Recap Workflow:
  collect wins/questions/challenges -> draft recap -> admin approve -> post

Deliverables:
- lib/rag/workflows/*
- lib/rag/tools/*
- app/admin/rag/workflows/page.tsx
- rag_workflow_runs and rag_workflow_steps migration if needed.
- Human approval UI.

Tests:
- Unit tests for each graph path.
- Interrupt/resume test for admin approval.
- Dead-letter test for failed tool call.
- End-to-end dry-run for weekly recap workflow.

Exit Gate:
- Agent workflows never publish without approval.
- Workflow runs are inspectable.
- Failed workflows do not lose state.


GLOBAL ACCEPTANCE CRITERIA
The RAG system is production-ready only when all are true:

1. Source capture works.
2. Ingestion is idempotent.
3. Chunks are embedded and searchable.
4. Retrieval returns cited chunks.
5. Answers include citations.
6. Weak-context questions refuse or ask clarification.
7. Discord command works safely.
8. Admin can inspect, approve, and correct.
9. Content queue is fed by real question patterns.
10. Evals pass before any prompt/retrieval change is shipped.
11. Railway worker remains healthy.
12. No dead-letter backlog grows silently.
13. Message Content Intent is enabled and verified if normal Discord message content is expected.

FRAMEWORK DECISION SUMMARY

LlamaIndex TS:
Use for design patterns around ingestion, chunking, indexing, query engine patterns, and source/citation handling. Keep the production path local unless LlamaIndex removes real complexity.

DeepSeek:
Use for answer drafting, content briefs, weekly recaps, quizzes, challenge generation, and other generation-heavy workflows.

LangGraph:
Use later for long-running, stateful, human-approved workflows.

LangChain:
Use selectively for tools, integrations, and model wrappers if it reduces code.

Haystack:
Do not use in the first implementation. It is stronger if we create a separate Python RAG service.

RAGFlow:
Do not use in the first implementation. Consider later only if complex PDFs become a major source type and visual ingestion UI is worth operating.
